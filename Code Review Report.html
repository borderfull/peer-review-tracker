Security

Critical Client controls the system prompt — API key can be used for arbitrary purposes analyze.js

The API handler accepts the system field directly from the request body and passes it unchanged to Claude. This means any caller — not just your frontend — can craft an arbitrary system prompt using your Anthropic API key. Someone could use it to run a general-purpose AI assistant, generate harmful content, or rapidly drain your credits.

Current code — dangerous
// pages/api/analyze.js
const { system, user } = body;
// ↑ system comes straight from the HTTP body — any caller controls this

const claudeResponse = await callClaudeAPI(user, system);
Fix

Remove system from the accepted body entirely. Hardcode the system prompt in the API file so it cannot be overridden. Only accept user (the reviewer feedback) from the client.

@@ pages/api/analyze.js @@
- const { system, user } = body;
+ const { user } = body;
+ const system = SYNTH_SYSTEM; // hardcoded here, not from client

Move the SYNTH_SYSTEM constant from tracker-utils.jsx into analyze.js on the server. The frontend never needs to send or know the system prompt.

Critical Server-side rate limit resets on every cold start — easily bypassable analyze.js

The rateLimitStore is an in-memory Map that lives in the serverless function's process. On Vercel, every cold start creates a fresh Map. The effective daily limit is therefore zero server-side — the only real enforcement is localStorage in the browser, which any user can clear in DevTools or bypass by calling /api/analyze directly with curl or a script.

// resets to empty on EVERY cold start
const rateLimitStore = new Map();

// The code itself documents the problem:
// ⚠️ PRODUCTION WARNING: This in-memory Map is NOT persistent across cold starts.
Fix — the upgrade path is already in your comments

Install Vercel KV (Redis-backed key-value store). The code already documents the 3-step upgrade path. This is a one-afternoon task and is the only reliable server-side enforcement.

# 1. Create a KV store
vercel kv create rate-limit-store

# 2. Install the client
npm install @vercel/kv

# 3. Replace Map reads/writes
import { kv } from '@vercel/kv';
const entry = await kv.get(`rl:${ip}`);
await kv.set(`rl:${ip}`, newEntry, { ex: 86400 });
High No input size limits — payload can exhaust API credits analyze.js

The user and system fields are validated for type but not length. A caller can send megabytes of text in a single request. This maps directly to Claude API token costs and could exhaust your credit balance with a small number of requests.

Fix

Add a character limit check before calling the API. 50,000 characters covers any realistic reviewer feedback; anything larger is almost certainly abuse.

const MAX_USER_CHARS = 50_000;

if (user.length > MAX_USER_CHARS) {
  return res.status(400).json({
    error: { message: `Feedback too long. Maximum ${MAX_USER_CHARS.toLocaleString()} characters.` }
  });
}
High CORS does not block non-browser clients analyze.js

The CORS logic in getCORSHeaders restricts which browser origins can call the API, but CORS is a browser mechanism. Any tool that doesn't send an Origin header — curl, Postman, Python scripts — reaches the handler with no restriction whatsoever. Since the API has no authentication, it is effectively a public API that anyone can call.

Combined with finding #1 (client-controlled system prompt) and #2 (in-memory rate limiting), this means the API is open to unauthenticated, unrestricted use.

Fix

For personal/experimental tools: the Vercel KV rate limit (finding #2) will mitigate the worst abuse. For a more robust solution, add a static shared secret: require a custom header (X-App-Secret) that the frontend sends and the server validates. It's not cryptographically strong but it stops casual scrapers.

Medium Race condition in concurrent rate limit checks analyze.js

The check-then-increment pattern in checkRateLimit is not atomic. Two simultaneous requests from the same IP can both read count < RATE_LIMIT_MAX before either increments it, allowing both through. On a serverless platform with concurrent invocations this is a real scenario.

// Both requests read ipEntry.count = 1 (below limit of 2)
// Both pass the check and increment separately → both succeed
ipEntry.count += 1; // ← not atomic
Fix

Vercel KV's atomic increment (kv.incr) solves this naturally. If staying with in-memory for now, accept the race as a known limitation of the current architecture.

The project requires at least two environment variables (ANTHROPIC_API_KEY, NEXT_PUBLIC_APP_URL) but there is no .env.example file. A new contributor or a fresh deployment has no discoverable reference for what to set.

Code Quality

High All dependencies pinned to "latest" — non-reproducible builds package.json

Using "latest" for next, react, and react-dom means every npm install — including each Vercel deployment — can pull a different version. A breaking release of Next.js or React could silently break your app on the next deploy.

@@ package.json @@
- "next": "latest",
- "react": "latest",
- "react-dom": "latest"
+ "next": "15.3.2",
+ "react": "18.3.1",
+ "react-dom": "18.3.1"

Also commit a package-lock.json (or yarn.lock) so every install is identical, and enable Dependabot to get notified of updates.

Medium shapeResult() duplicated between frontend and backend analyze.js · tracker-utils.jsx

The shapeResult function — which validates and normalises the Claude JSON response into theme objects — exists in both pages/api/analyze.js and public/tracker-utils.jsx with identical logic. Any bug fix or logic change must be applied in both places.

Since the backend already returns shaped data in the themes field of its response, the frontend's copy of shapeResult is unreachable dead code (the frontend callAPI function discards data.themes and re-parses data.text itself). The frontend should simply consume data.themes directly.

Fix

Keep shapeResult only in analyze.js. Update the frontend's parseAllFeedback and parseSingleFeedback to read data.themes from the API response instead of re-parsing and re-shaping the raw text.

@@ tracker-utils.jsx — parseAllFeedback @@
- const text = await callAPI(userMsg, SYNTH_SYSTEM);
- const match = text.match(/\{[\s\S]*\}/);
- if (!match) throw new Error("AI did not return valid JSON.");
- return shapeResult(JSON.parse(match[0]));
+ return await callAPI(userMsg); // callAPI now returns data.themes
Medium Array index used as React key — causes broken state on remove tracker-components.jsx

In OnboardingPage, reviewer textarea rows are keyed by array index (key={i}). When a user removes Reviewer 1 from a three-reviewer list, React reconciles by index — Reviewer 2's textarea now occupies index 0 and Reviewer 3 occupies index 1. If there was unsaved text, React will associate it with the wrong inputs.

// ❌ index as key — breaks on remove
{feedbacks.map((fb, i) => (
  <div key={i}>
))}

// ✅ stable ID as key
{feedbacks.map((fb) => (
  <div key={fb.id}>
))}
Fix

Change the feedbacks state from string[] to {id: string, text: string}[]. Generate a stable ID (crypto.randomUUID() or your existing generateId()) when each reviewer is added. Use fb.id as the key.

Medium window used as a module system — load-order fragile and namespace polluting all .jsx files

Every JSX file ends with Object.assign(window, { ... }) and every component reads shared values via window.C, window.IMPORTANCE_DOT, window.getDailyQuests etc. This creates a tight implicit dependency on script load order. If any script loads before its dependency, the component silently reads undefined at render time. There is also no tree-shaking or dead-code elimination — everything gets attached to window on page load.

Fix (long-term)

Migrate the app into proper Next.js pages using ES module imports. Each component imports only what it needs. This also enables pre-compilation of JSX (eliminating the browser Babel overhead — see finding #11).

Low Runtime Babel transpilation adds ~1MB overhead in production public/app.html

The app loads @babel/standalone (~1 MB minified) to transpile JSX in the browser at page load. This is appropriate for prototypes and sandboxes, but in a deployed product it means users wait for a large bundle to download and execute before any React code runs. It also makes DevTools error messages harder to follow since line numbers refer to the transpiled output.

Fix

Move the JSX into the pages/ or components/ directory and let Next.js compile it at build time. The result is pre-compiled JS with no browser transpilation step, smaller bundles, and source maps.

Low No React error boundary — any render error crashes the whole app tracker-app.jsx

There are no ErrorBoundary components anywhere. If a theme card, the summary panel, or any child throws at render time, React will unmount the entire tree and the user sees a blank page with no recovery path.

Fix

Wrap the tracking view in an error boundary that shows a friendly "Something went wrong — try refreshing" message and optionally surfaces the error details in development mode.

class ErrorBoundary extends React.Component {
  constructor(props) { super(props); this.state = { error: null }; }
  static getDerivedStateFromError(e) { return { error: e }; }
  render() {
    if (this.state.error) return <ErrorScreen error={this.state.error} />;
    return this.props.children;
  }
}

Best Practices & Architecture

Medium Unusual architecture — Next.js used only as an API proxy pages/index.js

pages/index.js immediately redirects to /app.html — a static HTML file. Next.js is not being used for routing, rendering, bundling, or HMR. You're getting the overhead of a Next.js server with none of its benefits. The real app is a static HTML file with CDN-loaded React compiled in the browser.

This works but leaves significant performance and DX improvements on the table:

  • No automatic code splitting
  • No server-side rendering or static generation
  • No hot module replacement during development
  • No production bundle optimisation
Recommendation

Migrate the frontend into pages/index.js (or app/page.jsx for the App Router) and import components from components/. This is a medium-effort refactor that makes the codebase conventional and unlocks the full Next.js toolchain.

Low System prompt is a public static file — users can read and replicate it tracker-utils.jsx

The SYNTH_SYSTEM constant is in a public static JSX file, making it trivially readable by anyone who opens DevTools or views source. More importantly, it is currently sent from the frontend to the backend with every request (see finding #1), meaning any caller can swap it for their own prompt.

For an open-source project this may be intentional, but it's worth making it a deliberate choice rather than an oversight.

Fix

Move SYNTH_SYSTEM into analyze.js on the server as part of fixing finding #1. It will no longer appear in any client-side file.

Low generateId() has a low but non-zero collision risk tracker-utils.jsx · analyze.js

Task and theme IDs are generated with Date.now().toString(36) + Math.random().toString(36).slice(2, 6). Math.random() only contributes 4 base-36 characters (~21 bits of entropy). If the page generates many IDs within the same millisecond (e.g. a response with 20+ tasks), duplicates are statistically possible and would cause React key collisions and broken toggles.

Fix

Use crypto.randomUUID() (available in all modern browsers and Node.js 14.17+) for guaranteed uniqueness.

@@ tracker-utils.jsx @@
- function generateId() { return Date.now().toString(36) + Math.random().toString(36).slice(2, 6); }
+ const generateId = () => crypto.randomUUID();
Info No tests — zero coverage across the codebase repo root

There are no test files in the repository. The most error-prone logic — rate limiting, shapeResult validation, mergeIntoThemes deduplication, getDailyQuests seeded randomness — has no automated verification and could regress silently on any refactor.

Recommendation — start small

Add Vitest (zero-config with Next.js) and write unit tests for the pure utility functions first: shapeResult, mergeIntoThemes, getLevel, checkRateLimit. These are the highest-value, lowest-effort tests.
